# VPS Manager 1.0.0

Интерактивный менеджер Debian 12/13 и Ubuntu 22.04/24.04 для установки и обслуживания 3x-ui/Xray, Reality, каскада RU → EU, сети, сертификатов и безопасности. Все 11 разделов меню подключены к операциям. Изменения выполняются на том VPS, где запущен менеджер; доступ к чужой удалённой панели не заменяет локальный резервный снимок.

## Установка и запуск

Распакуйте дистрибутив на VPS. Требуется установленный Python 3.10 или новее (входит в заявленные ОС), systemd и root. В Python используются только стандартные библиотеки; чтение существующего netplan-профиля DNS использует системный `python3-yaml`, обычно установленный вместе с netplan.

```sh
cd VPS-Manager
sudo sh install.sh
sudo vps-manager
```

Можно запускать без установки:

```sh
sudo sh vps-manager.sh
```

Установщик копирует исходники в `/opt/vps-manager/releases/<id>`, атомарно переключает `/opt/vps-manager/current` и создаёт `/usr/local/bin/vps-manager`. Он не меняет сеть, firewall или настройки панели. Общие конфигурации хранятся в `/etc/vps-manager`, состояние и копии — в `/var/lib/vps-manager`, события — в `/var/log/vps-manager/events.jsonl`.

## Как устроен откат

Перед рискованной операцией показывается действие и запрашивается подтверждение. Затем создаётся копия только затрагиваемых путей и устанавливается отдельный systemd timer с абсолютным временем и `Persistent=true`. Он не зависит от SSH-сеанса. Исполнитель отката копируется в приватный каталог транзакции, поэтому обновление программы не меняет уже запланированный откат.

После изменения выполняются проверки. Для сети, firewall и SSH требуется открыть новый сеанс и подтвердить доступ. Без подтверждения таймер останавливает незавершённый процесс применения и его дочерние процессы, восстанавливает файлы и выполняет команды восстановления. При ошибке восстановления systemd повторяет попытку, а состояние остаётся `failed` для диагностики. Новая рискованная операция при незавершённой транзакции блокируется.

```sh
sudo vps-manager transactions
sudo vps-manager rollback ИДЕНТИФИКАТОР
sudo systemctl list-timers 'vps-manager-rollback-*'
```

Не удаляйте каталоги активных транзакций. Для аварийного доступа используйте консоль провайдера. Откат не заменяет снимок диска у провайдера и не может исправить недоступность самого VPS или отказ диска. `apt upgrade` выполняется отдельно и не объявляется обратимой транзакцией.

## Первый запуск панели

Новая панель привязывается к `127.0.0.1`, получает случайный пароль и webBasePath. Данные сохраняются с правами 0600 в `/var/lib/vps-manager/panel-access.json`. Для первого входа используйте SSH-туннель:

```sh
ssh -L 2053:127.0.0.1:2053 root@IP_СЕРВЕРА
```

Откройте локальный URL с путём из файла. Если выбран другой порт, замените 2053. Перед внешней привязкой настройте сертификат. Мастер конфигурации не открывает HTTP-панель наружу без HTTPS.

API поддерживает cookie-сессию, 2FA и CSRF новых версий 3x-ui. Ввод пароля и VLESS URI скрыт. Настройки Xray сохраняются через `panel/xray/update`, inbound — через `panel/api/inbounds/add`; редактирование сгенерированного `config.json` и прямое изменение таблиц настроек SQLite не используются. Для изменяющих операций URL панели должен разрешаться в локальный адрес этого VPS.

## Сеть и классификация RU

Указывайте только реально выделенный провайдером адрес, точный CIDR и шлюз. `/32` не преобразуется в `/24`. Старые адреса не удаляются автоматически. Пробная таблица сначала проверяет новый источник, не меняя действующий default. Если старый маршрут имеет metric 0, используется отдельная таблица и правила для выбора нового исходящего адреса; ответы со старых локальных адресов сохраняют прежнюю таблицу. Постоянные адреса/маршруты записываются в профиль действующего сетевого менеджера. Неоднозначная существующая policy routing/VPN останавливает автоматический мастер.

Для netplan нужно указать ID из `netplan get`, который может отличаться от имени интерфейса. После плановой перезагрузки выполните:

```sh
sudo vps-manager network-verify
```

Шаблон RU использует `domain:ru`, `domain:su`, `domain:xn--p1ai` и `geoip:ru`. В официальной geosite.dat группа `ru` отсутствует; программа не генерирует неработающее `geosite:ru`. Домены других зон классифицируются по IP после DNS либо добавляются в пользовательские исключения. Это не гарантирует юридическую или организационную принадлежность сайта к стране. Порядок правил выбирается явно: при `last` старое широкое правило может перехватить трафик, при `first` каскад получает приоритет перед прежними правилами выбранных inbound. Системные маршруты VPS при настройке каскада не меняются.

## Сертификаты

Для HTTP-01 нужен доступный извне TCP 80. Менеджер не останавливает занимающий порт сервис автоматически. Выберите существующий сертификат либо предварительно согласуйте освобождение порта. Для IP-сертификатов нужен публичный IP и поддержка профиля `shortlived`; используется раннее продление. Автоматическое продление зависит от доступности CA и порта 80. После смены IP перевыпустите IP-сертификат через раздел SSL.

## Осознанные ограничения

- Поддерживается стандартная локальная установка 3x-ui с SQLite в `/etc/x-ui/x-ui.db` и бинарниками в `/usr/local/x-ui`. Docker, PostgreSQL, перенесённые пути и нестандартные systemd unit не должны автоматически приниматься за такую установку.
- Произвольные версии панели и Xray не гарантированно совместимы. Перед изменением проверяются архив, бинарник и конфигурация; при ошибке восстанавливается согласованная копия. Существующий релиз не заменяется на latest, если запрошенный тег отсутствует.
- Существующие сторонние nftables/iptables конфигурации показываются, но не заменяются UFW. Их автоматическая перестройка без знания политики могла бы заблокировать администратора. Управляйте ими через действующий инструмент.
- Проверка шлюза использует ICMP. Если провайдер его фильтрует, мастер прекращает изменение до смены маршрута; уточните профиль у провайдера.
- Внешний вход по SSH, поведение сети после реальной перезагрузки и доступность ACME извне требуют проверки на конкретном VPS. Локальный тест не выдаётся за такую проверку.
- Исходники опубликованы в **arsa11/-vps-tools**. Самообновление из локального дистрибутива работает; для обновления через GitHub нужны опубликованные Releases с архивом и SHA256. После создания таких релизов создайте `/etc/vps-manager/update.json` с полями `repository` (`owner/repo`) и `asset` (`vps-manager.tar.gz`).

## Команды и диагностика

```sh
sudo vps-manager diagnose
sudo vps-manager diagnose --online --json --output /root/vps-report.json
sudo vps-manager backup
sudo vps-manager list-backups
sudo vps-manager verify /var/lib/vps-manager/backups/ИМЯ
sudo vps-manager restore
sudo vps-manager quick-setup
```

Диагностика возвращает код 1 при ERROR. WARN не обязательно означает неисправность: отсутствие IPv6 может быть нормальным. Копии содержат секреты и должны храниться защищённо; права каталогов 0700, файлов 0600. В лог событий попадают названия операций и идентификаторы транзакций, а не пароли или содержимое конфигураций.

## Архитектура и тестирование

`install.sh` и `vps-manager.sh` — оболочки запуска; `modules/*.sh` — отдельные точки входа. Основная логика в `vpsmanager/*.py`: стандартная библиотека Python используется для строгого JSON, безопасных аргументов subprocess, SQLite backup, атомарных файлов и проверяемых транзакций. Это осознанное отличие от предложенных в ТЗ Bash-библиотек; внешние зависимости Python не нужны для основной работы.

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q vpsmanager
python3 build_release.py
```

Дополнительные тесты настоящего Xray включаются переменной `VPS_MANAGER_TEST_XRAY=/путь/к/xray`; для локального TLS-стенда нужен OpenSSL. Тест `tests/systemd_smoke.py` запускайте только в одноразовом systemd-контейнере с `VPS_MANAGER_DISPOSABLE_TEST=1`. GitHub Actions содержит матрицу четырёх ОС и отдельный тест независимого таймера. Факт наличия workflow не означает, что удалённый CI уже выполнялся; результаты текущей проверки перечислены в `ACCEPTANCE.md`.
